# K8s Dashboard — Plan & Implementation Log

A web app (Angular UI + .NET 10 API backend) for browsing **any number of Kubernetes clusters** — nodes, namespaces, pods, deployments, services, events, pod logs, pod exec — without SSH-ing into any server. Builds directly on what `k8s-console-tool` proved out (same underlying `KubernetesClient` approach), but as a proper multi-user, multi-cluster web app instead of a single-operator console menu.

---

## 1. The core design question: what makes this "generic"?

The requirement is explicit: it must work against **any** cluster — this WSL2 lab cluster today, clusters on RHEL 9 or RHEL 10 servers tomorrow, anything else later — without code changes per cluster.

**Decision: a cluster is identified purely by its kubeconfig.** Not by "RHEL 9 cluster" vs "RHEL 10 cluster" special-casing, not by hardcoded IPs, not by assuming a particular auth method. Reasoning:

- Kubeconfig is the **standard, complete description** of how to reach and authenticate to a cluster: server URL, CA certificate, and credentials in whatever form that cluster uses (client cert/key, bearer token, or an `exec` plugin for things like cloud IAM tokens). Every Kubernetes distribution produces one, regardless of what OS the control plane runs on.
- The **client-side OS distinction (RHEL 9 vs RHEL 10 vs anything else) is irrelevant to this app** — that's the *server's* OS, and Kubernetes' API is identical regardless. The app never needs to know or care what OS a cluster's nodes run. This is exactly why talking to the API server (like `kubectl` does) rather than SSHing into boxes is the right approach — it's the one interface guaranteed to be the same everywhere.
- So "generic" reduces to one concrete engineering decision: **store a kubeconfig per registered cluster, build a Kubernetes client from it on demand, and never hardcode anything about what's on the other end.**

**Practical consequence:** registering a new cluster (RHEL-hosted or otherwise) is just: get its kubeconfig (already sitting at `~/.kube/config` on whatever machine runs `kubectl` against it, or generated by the cluster's setup process — kubeadm, RKE2, OpenShift, etc. all produce one), paste it into this app, give it a name. No installers, no agents on the target cluster.

## 2. Persistence: the "provision to update it in backend"

Registered clusters need to survive an API restart, and need to be addable/editable/removable through the app itself (not by editing a file on the server by hand).

**Decision: a small JSON file-backed store** (`data/clusters.json`), not a full database. Reasoning:
- The data shape is trivial (a handful of clusters, each just `{id, name, description, kubeconfigYaml, createdAt}`) — a real RDBMS would be pure overhead for this scale.
- It's still fully "provisioned through the backend": a `ClustersController` exposes CRUD endpoints, and the store is the thing those endpoints read/write. Nobody needs file access to add a cluster.
- **Security note, stated plainly rather than glossed over:** kubeconfigs contain credentials. A plaintext JSON file is an acceptable tradeoff for a local learning/ops tool exactly like a kubeconfig file on disk already is (which is exactly how `kubectl` itself stores credentials) — but a real production deployment of this tool would want the store encrypted at rest or backed by a proper secrets manager (Kubernetes Secrets + Sealed Secrets, HashiCorp Vault, etc.). Flagging this now rather than pretending it's a solved problem.

## 3. Backend design

**`K8sDashboard.Api`** — ASP.NET Core 10 Web API.

### 3.1 Cluster registry
- `Models/ClusterConfig.cs` — `Id` (guid), `Name`, `Description`, `KubeconfigYaml` (raw text, exactly as copy-pasted from `kubectl config view --raw --flatten`), `CreatedAt`.
- `Services/ClusterConfigStore.cs` — reads/writes `data/clusters.json`. A `SemaphoreSlim` guards concurrent writes (multiple browser tabs could register clusters at once).
- `Controllers/ClustersController.cs`:
  | Method | Route | Purpose |
  |---|---|---|
  | GET | `/api/clusters` | list registered clusters (never returns the raw kubeconfig — see 3.4) |
  | POST | `/api/clusters` | register a new cluster |
  | PUT | `/api/clusters/{id}` | update a cluster's kubeconfig/name/description |
  | DELETE | `/api/clusters/{id}` | remove a cluster |
  | GET | `/api/clusters/{id}/test` | verify connectivity (attempts a namespace list, reports success/failure) |

### 3.2 Per-cluster Kubernetes client
- `Services/ClusterClientFactory.cs` — given a cluster id, loads its stored kubeconfig, builds an `IKubernetes` client via `KubernetesClientConfiguration.BuildConfigFromConfigFile(Stream)` (a `MemoryStream` over the stored YAML text — no temp files), and **caches** the built client per cluster id (`ConcurrentDictionary<Guid, IKubernetes>`). Cache entry is invalidated whenever that cluster's config is updated or deleted, so editing a kubeconfig actually takes effect on the next request rather than silently keeping a stale connection.

### 3.3 Kubernetes queries — reusing what `k8s-console-tool` already proved
- `Services/KubernetesQueryService.cs` — the exact same method shapes as `k8s-console-tool`'s `KubernetesService` (`GetNodesAsync`, `GetPodsAsync(namespace)`, `GetPodLogsAsync(...)`, `ExecInPodAsync(...)`, `GetDeploymentsAsync`, `GetServicesAsync`, `GetEventsForObjectAsync`/`GetEventsAsync`), except every method now takes an `IKubernetes client` parameter instead of holding one client for its whole lifetime — because this backend serves *many* clusters, not one. This is the one structural difference from the console tool; the Kubernetes-API-calling logic itself is identical, since it already generalizes to any cluster (that was true even in the console tool — a cluster was just whatever kubeconfig you pointed it at).
- `Controllers/K8sController.cs` — routes nested under a cluster id, e.g. `/api/clusters/{clusterId}/nodes`, `/api/clusters/{clusterId}/namespaces/{ns}/pods`, `/api/clusters/{clusterId}/namespaces/{ns}/pods/{pod}/logs`, `/api/clusters/{clusterId}/namespaces/{ns}/pods/{pod}/exec` (POST, body = command string), `/api/clusters/{clusterId}/namespaces/{ns}/deployments`, `.../services`, `/api/clusters/{clusterId}/events`.

### 3.4 What the API deliberately never returns
`GET /api/clusters` and friends never send the stored `KubeconfigYaml` back to the browser in list/get responses — only on the specific update flow where the UI needs to prefill an edit form. Reduces the chance of credentials ending up in a browser's network-tab history or a casual screenshot.

## 4. Frontend design

**`k8s-dashboard-ui`** — Angular (same major version/toolchain as the product-catalog app), standalone components.

- **Cluster picker** (top-level): list of registered clusters + "Add Cluster" (name, description, a textarea for pasting kubeconfig YAML, "Test Connection" before saving).
- Once a cluster is selected, a **dashboard layout** — left-hand nav for the resource types (Nodes, Namespaces, Pods, Deployments, Services, Events), main panel showing a table for whatever's selected.
- **Pods view** drills down: pick a namespace → table of pods → click a pod → detail panel (containers, status, events) with **Logs** and **Exec** tabs (tail-line count input for logs; a command input + "Run" button for exec, output shown in a `<pre>` block).
- Design language: a clean, dense **admin/ops dashboard** look (sidebar nav, plain data tables, monospace log/exec output) rather than the product-catalog app's playful gradient styling — appropriate for a tool whose job is showing a lot of live operational data clearly, not selling a product.
- Talks to the backend via a relative `/api` base URL + dev-server proxy (`ng serve` → `proxy.conf.json`) — the exact same pattern used for the product-catalog frontend, for the same reason (works unchanged if this is later containerized/deployed).

## 5. What's explicitly out of scope for now

- **Authentication/authorization on the dashboard itself** — anyone who can reach this app's UI can browse (and exec into) every registered cluster. Fine for a local/trusted-network tool; a shared deployment would need its own login layer plus per-user cluster access control. Noted, not built.
- **Editing/creating resources** (no "delete this pod" or "scale this deployment" button) — this is a read/observe tool, matching the console tool's scope. Extending to write operations is a natural next step but a deliberately separate one (write operations need confirmation flows, RBAC awareness, and much more careful error handling than a read-only browser).
- **Real-time streaming logs/exec** (this reuses the same one-shot "fetch N lines" / "run one command, get output" model as the console tool, not a live tailing WebSocket in the browser). A reasonable v2 enhancement once the basic read path is solid.

## 6. Implementation order

1. Backend: models, JSON store, client factory, query service, controllers — verified via Swagger/curl against the real `k8slab` cluster (register it using the kubeconfig already generated for `k8s-console-tool`) before any UI exists, same discipline as the product-catalog backend.
2. Frontend: cluster registration flow first (nothing else works without a registered cluster), then the resource browser views.
3. End-to-end verification in a real browser (Playwright, as used for the product-catalog app) — register the live cluster through the UI, browse to its pods, pull real logs.

### What this proves about "generic"
The backend and frontend were both written and tested without a single line of code that knows anything is a "WSL2 minikube lab cluster" specifically — the only WSL2-specific fact anywhere in this flow is the *kubeconfig's server URL* pointing at a local tunnel, which is exactly the kind of detail kubeconfig exists to encapsulate. Pointing this same app at a cluster on a RHEL 9 or RHEL 10 server requires zero code changes: get that cluster's kubeconfig, paste it into the "Add Cluster" form, done.
